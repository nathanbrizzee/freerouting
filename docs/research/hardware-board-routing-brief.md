# Hardware board routing brief: requirements, workarounds, and answers from the source

Status: reference input for the router overhaul (`router-overhaul-roadmap.md`). Recorded 2026-10-19.

Source: a brief written 2026-10-18 by the Claude agent that routes four boards for the user (nathanbrizzee)
with Freerouting v2.5.0. It is condensed here; every number is from that brief. The brief's own sources (the
hardware repo's `tools/kicad/pcb_route.py`, `pcb_link.py` and run-history CSV) are not in this repository.
Section 6 adds the answers found in the Freerouting source. Code paths are relative to
`src/main/java/app/freerouting/` at master `5aa1b24`.

## 1. The boards

| Board | Layers | Size | Scale |
|---|---|---|---|
| Carrier | 6 | 404 x 286 mm | about 650 connections, 302 parts, 652 SMD pins fanned out, about 960 vias |
| Etch card | 6 | 98 x 122 mm | 4 identical channels, about 870 vias |
| Power card | 4 | 98 x 122 mm | one 20 A half-bridge |
| Motor card | 4 | 98 x 122 mm | DRV8462 stepper |

Everything is generated by script, with no hand routing, so the router must finish every board unattended.

- **Stackup (6 layers):** F signals, In1 solid GND plane, In2 signals (horizontal), In3 signals (vertical), In4 split
  power plane, B signals.
- **Vias:** through only, 0.6 mm pad, 0.3 mm drill.
- **Rules:** clearance 0.2 mm in every class. Class track widths from 0.2 mm to 2.0 mm.
- **High voltage:** 48 V and 72 V nets form a voltage group that needs 0.5 mm to every low-voltage net, expressed as
  `class_class` rules of 0.51 mm. One class pair (gate against dV/dt network) also needs 0.5 mm.
- **Current:** load-current classes are restricted to the outer layers, because 0.5 oz inner copper would need about
  twice the width.

## 2. Requirements (R1-R20)

| # | Requirement | Status in v2.5.0 |
|---|---|---|
| R1 | Honour per-class layer restrictions | Works |
| R2 | Honour `class_class` clearance for tracks, pads and the router's own vias | Tracks work; router vias do not (0.43 mm where 0.51 mm was required) |
| R3 | Honour a net-pair clearance | Works for tracks |
| R4 | Never produce clearance under the rule | 0.198 mm against 0.2 mm; 0.1956 mm between tracks |
| R5 | Power and ground pins get their vias first | Freerouting will not join an SMD pin to a plane layer |
| R6 | Fan out every pin before signals, straight out, planned for all pins together | Built-in fanout repeats passes with no progress; one 45-minute hang |
| R7 | Route in stages, each fixed before the next | Done by script |
| R8 | A plane region of net N is a target for N and an obstacle for every other net | Not supported |
| R9 | No single-layer vias, dead-end vias or dangling stubs | Left behind |
| R10 | Never neck below the board minimum | Necked to 0.1 mm at fine-pitch pins |
| R11 | One preferred direction per layer | `undesired_direction_trace_cost` has no effect |
| R12 | Keep the via count down | Trade-off through `start_ripup_costs` |
| R13 | Connect to fixed copper of the net anywhere | Does not join to the end or body of a fixed track |
| R14 | Keep switching loops short | No length or loop limit |
| R15 | Route a differential pair together | Scripted |
| R16 | Leave room for thermal spokes | Not supported |
| R17 | Respect keepouts, board edge and fiducials | Works for keepouts; KiCad does not export copper-to-edge |
| R18 | Finish long runs (60-240 mm) when there is room | Leaves them open |
| R19 | Deterministic | Freerouting itself was deterministic in every test |
| R20 | Must not hang | Hangs (section 3) |

## 3. Workarounds built around Freerouting

| Workaround | Why | Measured cost |
|---|---|---|
| Cropped-DSN window pass for leftovers (about 300 lines) | An uncropped window run chases every open connection of the window's nets across the board | One window 822 s uncropped, 82 s cropped. Even a tiny window costs about 20 s of router time (JVM start about 6 s plus 3 passes). |
| Staged routing with held nets (about 350 lines) | No "route only these nets" option. Dropping nets leaves stubs that get joined and pads without class rules. | Pour nets held in every stage cut the carrier power stage from 50 to 10 minutes. |
| Stall guard and no-via keepout over a Tag-Connect footprint | Hangs in `DrillPage.getDrills` → `PolylineArea.splitToConvex` (45 min in fanout, 40 min in pass 1), and a 25-minute silent stall after `PolygonShape.DivisionPoint: projection not found` | A lost window; legal via sites removed. |
| +10 um on every clearance and a post-route sliver neck-down | Clearance shortfalls of 2-4 um; round vias read as polygons cause 322-574 false "violations" per carrier stage (568 on the etch card) | Every board routes 10 um tighter than needed (25 um broke routing into 0.5 mm-pitch pins). Freerouting's violation count is useless as a check. |
| Iterative dangling and single-layer via removal under a KiCad DRC guard | Freerouting leaves them; its optimizer only runs on a board with 0 unrouted | Each via costs a connectivity rebuild; an earlier cruder version deleted good vias. |
| HV via padstack grown by 0.3 mm a side, mapped back after routing | Router vias ignore `class_class` | Fewer via sites in dense HV areas; SES rewriting. |
| Locked thermal stubs before routing | The router takes thermal spoke room | Starved pads 26 down to 0. The earlier post-route push fixed 1 pad in 1.7 hours. |
| Edge and fiducial keepouts | KiCad does not export copper-to-edge | Minor. |
| Grid maze router in Python (`pcb_link.py`, 0.25 mm grid, A*, preferred direction per layer, exact segment checks) before and after Freerouting | With inner layers about 98% empty, Freerouting still left 60-97 mm runs open, and rail-to-plane-region joins open | 65 links, 1624 mm, 1-50 s each. It closed every leftover connection across five full runs (six different nets). Cost: a second router; links take lanes from neighbouring pins. |
| Up to 4 cost variants side by side, early stop, rerun to the best pass | Pass 1 is usually the best and later passes get worse; the session is written only at the end | Etch card unrouted by `start_ripup_costs`: 30 gives 121, 100 gives 96, 300 gives 77, 1000 gives 65. Carrier stages: pass 1 best in all five (for example 114 / 125 / 125). |

Other observations:

- **JVM settings:** ParallelGC is 10-13% faster than G1, and `-Xmx1g` is 2-4% faster than 2-4 GB.
- **Optimizer threads:** `-mt N` does not set the optimizer threads; `--router.optimizer.max_threads=N` does.
- **Board edge:** a wire with a corner outside the board bounds is dropped.
- **Plane connections:** these end exactly on the pour outline.
- **Pours on signal layers:** these are not obstacles for other nets.
- **Cropped windows:** these report 11-27 unrouted when 1-2 connections are really open.

## 6. The brief's source questions, answered

"Confirmed" means read in the code. "Likely" means the code path fits, but no test has proved it yet.

### Clearance and geometry

1. **How are round shapes approximated?** Circles become their bounding octagon in the search trees and in DRC
   (`geometry/planar/Circle.java:108-142`), up to 8.24% outside the circle on the diagonals. Track ends are square
   caps with mitred bends (`geometry/planar/Polyline.java:44-51, 361`). Freerouting's own shapes are mostly larger
   than the real copper. A shortfall of a few micrometres most likely comes from pads exported as polygons whose
   chords cut inside the real arcs, plus integer rounding and the 1 um tolerance (`rules/BoardRules.java:52`).
   Likely, not proved.
2. **Where is a router via's clearance looked up?** From the net class's via rule and the via padstack's clearance
   class (`autoroute/maze/AutorouteControl.java:224, 249`). The checks themselves use the matrix correctly. The
   matrix is what's incomplete: a `class_class` rule without a type list sets only the entry named after the net
   class (`io/specctra/parser/Network.java:656-663`). The item sub-classes the via and pads actually use (`A$via`,
   `A$smd`, the default `smd` and `via` classes) never get it. Typed pairs repoint the via class after the via infos
   were built (`:551-558`, `:838-842`). Likely the cause of both the 0.43 mm vias and the unflagged 0.13 mm via at
   load. A two-class test board will prove it.
3. **Why does a clean board report 322-574 violations?** DRC is polygon-based. It enlarges octagons by half the
   clearance, intersects them, and finds the gap by a 16-step binary search (`board/model/items/Item.java:446-563`).
   Octagon diagonals and mitred corners read as smaller gaps than the real ones. Confirmed mechanism.
4. **Clearance compensation?** The autorouter builds one compensated search tree per trace clearance class
   (`board/searchtree/SearchTreeManager.java:140-171`). The default interactive tree is uncompensated unless the GUI
   turns it on. It changes speed, not the rules.

### Planes, pours, fixed copper

5. **Why can't a pin join a plane by via?** Non-signal layers are forced inactive (`AutorouteControl.java:155-161`).
   Target doors on inactive layers are skipped (`autoroute/maze/MazeSearchEngine.java:654`). A result on an inactive
   layer is rejected (`autoroute/maze/AutorouteEngine.java:221-227`). Pours on signal layers are conduction areas;
   whether they block other nets depends on their obstacle flag. Still to trace for the pour case.
6. **Why do plane connections end on the outline?** Pin-to-area contact needs the drill centre inside the area
   (`DrillItem.java:297-299`, `ConductionArea.java:348-353`), and the search stops at the first point that reaches
   the target shape. Likely, not proved.
7. **Can a fixed wire's end or body be a target?** The router can reach the body, but joining needs a trace split,
   and `PolylineTrace.split` returns null for fixed traces (`board/trace/PolylineTrace.java:727`). Contacts are
   exact-point only (`DrillItem.java:289`, `Trace.java:188`). That explains joining at a pad but not at a bare track
   end. Confirmed for the split.
8. **Why are overlapping same-net pads not connected?** `Pin.getNormalContacts` checks copper overlap but returns
   early for component 0 (`Pin.java:771`), and `Connection.get` requires equal centres (`DrillItem.java:333`).
9. **Why is a wire with a corner outside the board dropped?** `io/specctra/parser/Wiring.java:498-509` drops the
   whole wire. The board box is the outline plus 1000 units.

### Batch loop, passes, scoring

10. **Rip-up cost, and why passes 2-3 come out worse.** Cost is `start_ripup_costs x pass number`, linear with no
    cap (`autoroute/pipeline/AutorouteConnectionRouter.java:46`). Each pass starts from the current board, not the
    best. The best board is restored only from pass 8, on every 4th pass (`AutorouteBatchLoop.java:367-413`). Later
    passes get worse because rip-ups are destructive:
    - a route rejected by strict DRC (on from pass 3) leaves its victims ripped (`AutorouteConnectionRouter.java:299-314`);
    - a partial insert leaves its victims ripped (`autoroute/path/FoundConnectionInserter.java:97-106`);
    - a 2-pin net that fails twice rips its whole self (`AutoroutePassRunner.java:175-180`);
    - the randomization meant to break loops never runs, because `ripupPassNo` stays 1 (`AutorouteControl.java:189`).
11. **A region or "selected items" path?** The GUI `autorouteSelectedItems()` is an empty stub
    (`gui/workspace/controllers/GuiBoardLegacyEditActions.java:34`). `RoutingBoard.autoroute(Item, ...)` exists but
    nothing calls it. The inflated window counts are still to investigate: the count is per-net components minus one
    over all items (`drc/NetRoutingLedger.java`), so held fragments that are counted as unconnected pieces are the
    first suspect.
12. **Order, and limits per connection.** Items come in board-list order (roughly DSN order), plane nets first. From
    pass 2, nets incomplete last pass go first (`AutoroutePassRunner.java:257-322`). There is no expansion cap. The
    time limit is 100 s x 2^(pass-1). Why long runs fail on an empty board is still open; candidates are the weak
    heuristic (`DestinationDistance.java:102-293`), the fixed-copper target issue (question 7) and destructive
    rip-up. Case C7 is the test.
13. **Why does `undesired_direction_trace_cost` have no effect?** It biases only which rooms the search crosses. The
    final geometry comes from `FoundConnectionLocator45Degree` and `AnyAngle` plus pull-tight, which do not read it.
    The optimizer turns preferred directions off on alternate passes (`board/optimize/BatchOptimizer.java:406`). The
    settings layer stacks a board-specific add and does not re-apply later changes (`settings/RouterSettings.java:403-442`).
14. **Why is the optimizer gated on 0 unrouted?** The gate is `BatchOptimizer.java:163`; no reason is recorded.
    Running it on a partial board is safe if it is not allowed to lose a connection, and the incremental incomplete
    count now makes that check cheap.
15. **Where is the session written?** Only at the end of the job. `save_intermediate_stages` fires board events;
    only the GUI and API listeners consume them.

### Fanout, vias, output hygiene

16. **Fanout stop rule, and why the same 69 pins repeat.** A pin's escape rips a neighbour's, which re-escapes next
    pass, so the routed count never reaches 0. Each success bumps the component generation, which re-enables every
    failed pin of that component (`autoroute/BatchFanout.java:136-164, 276-332`). Per-pin time and rip-up cost rise
    each pass, up to 20 passes, and the fallbacks rerun fanout from scratch. The via must lie 2.5-4.5 mm from the pin
    (`MazeSearchEngine.java:88-121`).
17. **Single-layer vias and stubs.** A via whose contacts are all on one layer is a tail (`Via.java:171`). Dangling
    fanout vias are protected during passes (`RoutingBoard.java:1286`). The final cleanup that removes them is
    skipped on every stagnation, no-improvement or max-passes stop (`AutorouteBatchLoop.java:661` against `:747-752`).
    Confirmed. The neck width floor is still to trace.

### Robustness and determinism

18. **The hangs.**
    - **Via-site splitting.** `PolylineArea.splitToConvex` cuts every hole out of every piece, with no cap and
      without the per-connection time limit (`geometry/planar/PolylineArea.java:168-204`). Via sites around a footprint
      with many holes multiply the pieces.
    - **Failed polygon splits.** A failed `PolygonShape.splitToConvex` is not cached and returns null
      (`PolygonShape.java:552-613, 791-800`), so each later call redoes it and logs again. An area whose split fails
      gets no tree shapes and becomes invisible (`ShapeSearchTree.java:1103`).
19. **Threads.** The autorouter pass and fanout are single-threaded whatever `max_threads` says. Only the optimizer
    uses a pool, picking one best candidate per chunk.
20. **Why pass 1 is slower.** Pass 1 walks every item. Later passes only revisit incomplete nets.

### Rules from the DSN

21. **Which rule forms are honoured?** `class_class`, `use_layer` and `use_via` per class, and per-pin
    `clearance_class` are read; see question 2 for the `class_class` gap. A full audit of ignored forms is not done
    yet.
22. **Minimum width and maximum length?** There is no length or loop limit in the router.
